## 1. 系统目标

剧情大纲系统是**编剧 Agent 的核心输入**。它从旧版 CSV 事件配置表演进而来，解决三个根本问题：

1. **从"时刻表"升级为"节拍表"**：旧 CSV 写死了"W1 Day3-5 Morning 咖啡馆"，导致事件缺乏上下文感知。新大纲只描述"这段故事要讲什么"，具体时机和地点由编剧 Agent 根据 NPC 实时状态编排。

2. **赋予 NPC 真正的自主权**：NPC Agent 保留独立的 `think()` 决策——去哪、做什么、和谁互动。编剧 Agent 不架空 NPC，而是通过**软引导（记忆注入）+ 硬编排（仅在关键节点）**来确保大纲不偏离。

3. **让涌现叙事可控**：AI 可以参与事件生成，但大纲的结构、节拍的 `must_happen` 约束、`latest_by` 兜底机制保证了叙事骨架不散。

---

## 2. 与旧 CSV 的关系

| | 旧 CSV（事件配置表） | 新大纲（StoryOutline） |
|---|---|---|
| **定位** | 可执行的事件时刻表 | 编剧 Agent 的创作约束 |
| **触发方式** | 固定 Week/Day/Slot/Location 匹配 | 编剧 Agent 判断"时机合适" |
| **地点** | 写死 LocationId | `location_hint` 仅建议，编剧可灵活选择 |
| **灵活性** | 硬编码，错过就错过了 | `latest_by` 兜底但不限制提前 |
| **叙事意图** | 无（只有 delta 数值） | `what_must_happen` 告诉编剧"这段要表达什么" |
| **调性** | 无全局约束 | `tone_rules` 确保叙事情绪一致 |
| **NPC 关系** | 事件系统独立于 NPC 决策 | 编剧 Agent 读取 NPC 意图后再编排 |

**迁移策略**：旧 CSV 不会被删除。现有 55 条预定义事件作为"事件库"保留，编剧 Agent 可以把它们当作素材（prompt 中的 few-shot 示例）。但触发逻辑从 `match_events()` 的 5 层过滤切换为编剧 Agent 的 LLM 推理。

## 3. 整体架构

```
StoryOutline (本文件定义)
  ├── arcs: StoryArc[]              # 故事弧线
  │     └── beats: StoryBeat[]      # 叙事节拍
  ├── tone_rules: ToneRule[]        # 调性约束
  └── global_constraints: Constraint[]  # 全局限制

编剧 Agent 每时段工作流：
  1. 读取 StoryOutline + 当前周/日
  2. 收集所有 NPC 的 think() 意图
  3. 检查大纲：哪些 beat 到期了？哪些即将到期？
  4. 判断每个 NPC 的意图是否和大纲冲突
  5. 软引导（注入记忆）或硬编排（覆盖 location），生成事件列表
  6. 事件交给 execute_events() 结算
```

## 4. 数据格式

### 4.1 顶层结构

> **注意**：实现中简化了 JSON 格式。`earliest`/`latest_by` 对象改为平铺的 `earliest_day`/`latest_day` 整数，直接使用 day(1-60) 而非 `{week, day}` 嵌套。

```jsonc
{
  "version": "1.0",
  "game_days": 60,
  "weeks": 9,

  "arcs": [
    { /* StoryArc */ }
  ],

  "standalone_beats": [
    { /* StoryBeat */ }
  ],

  "tone_rules": [
    { /* ToneRule */ }
  ],

  "global_constraints": {
    "max_events_per_slot": 3,
    "max_events_per_npc_per_day": 2,
    "anchor_priority_over_npc_intent": true
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `version` | string | 大纲格式版本 |
| `game_days` | int | 游戏总天数，固定 60 |
| `weeks` | int | 总周数，固定 9 |
| `arcs` | StoryArc[] | 故事弧线列表，每条弧线跨越数周 |
| `standalone_beats` | StoryBeat[] | 不挂靠特定弧线的独立节拍（如开场、终局） |
| `tone_rules` | ToneRule[] | 全局调性约束，编剧 Agent 必须遵守 |
| `global_constraints` | object | 硬限制（防止一个时段塞太多事件） |

### 4.2 StoryArc —— 故事弧线

```jsonc
{
  "id": "cult_infiltration",
  "name": "邪教渗透线",
  "description": "顾沉舟潜入归潮镇，逐步拉拢岛民，建立邪教网络",
  "weeks": "W2-W7",                          // 弧线覆盖的周范围
  "priority": 1,                              // 优先级，数字越小越高（锚点=0）
  "key_npcs": ["gu_chenzhou", "chen_haisheng", "jiang_xueyi"],
  "ending_condition": "cult_influence >= 80 OR gu_chenzhou_arrested",
  "beats": [
    { /* StoryBeat */ }
  ]
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一标识，如 `cult_infiltration` |
| `name` | string | 中文名称 |
| `description` | string | 弧线的叙事概要，用于编剧 Agent 的 prompt 上下文 |
| `weeks` | string | 覆盖的周范围，如 `"W2-W7"` |
| `priority` | int | 弧线优先级。0=锚点（必须完成），1=主线，2=支线 |
| `key_npcs` | string[] | 弧线的核心 NPC |
| `ending_condition` | string | 弧线的结束条件（自然语言），编剧 Agent 据此判断弧线是否该收束 |
| `beats` | StoryBeat[] | 弧线内的叙事节拍，按顺序排列 |

### 4.3 StoryBeat —— 叙事节拍

这是大纲的核心原子单元。每个 beat 描述一段必须发生的叙事事件。

> **实现简化**：`earliest_day`/`latest_day` 直接使用 1-60 的天数（而非 `{week, day}` 嵌套对象）。`event_id` 指向 CSV 事件时可复用其 outcomes，无需在 beat 中重复定义。

```jsonc
{
  "id": "gus_approach_chenhai",
  "name": "顾沉舟接触陈海生",
  "type": "key",                              // anchor | key | opportunity

  // ── 引用已有 CSV 事件（可选）──
  "event_id": "w2_gus_approach_chenhai",      // 指向 事件配置表.csv 的 EventId。
                                               // 为空则表示大纲新增事件，需 inline outcomes

  // ── 时机约束（简化格式）──
  "earliest_day": 12,                          // 最早可触发日 (1-60)
  "latest_day": 14,                            // 最晚触发日
  "preferred_slot": "night",                   // 建议时段
  "preferred_location_hint": "port",           // 建议地点（可选）

  // ── 参与者 ──
  "participants": ["gu_chenzhou", "chen_haisheng"],
  "required_participants": true,              // true=必须全员到场，false=至少一人即可

  // ── 触发条件 ──
  "prerequisites": [
    "gus_arrive.completed",                   // 前置 beat 必须已完成
    "gu_chenzhou.location != arrested"         // 自然语言条件
  ],
  "block_if": [
    "gu_chenzhou.trust < 10",                 // 如果顾沉舟已暴露，跳过此 beat
    "chen_haisheng.dead"                       // 陈海生已死亡则跳过
  ],

  // ── 叙事意图 ──
  "what_must_happen": "顾沉舟在港口附近主动接触陈海生，以'同为底层劳动者'的身份拉近距离，煽动陈海生对生活的不满，暗示他'有另一种活法'。",
  "narrative_goal": "建立顾沉舟-陈海生的怨气连接，为后续邪教转化埋下伏笔。陈海生应产生好奇心或轻微认同，但不立即加入。",

  // ── 结果分支 ──
  "outcomes": [
    {
      "id": "gus_chenhai_success",
      "condition": "default",
      "description": "陈海生对顾沉舟的话产生兴趣，怨气值上升",
      "resource_delta": { "cult_influence": 5 },
      "bond_delta": { "bond_guchenzhou_chenhaisheng": 10 },
      "karma_delta": { "chenhai_cult_line": 8 },
      "npc_state_delta": { "chen_haisheng": { "happiness": -3 } }
    },
    {
      "id": "gus_chenhai_resist",
      "condition": "divine_intervention",
      "description": "陈海生觉得顾沉舟的话不对劲，暂时警惕",
      "resource_delta": { "cult_influence": 2 },
      "bond_delta": { "bond_guchenzhou_chenhaisheng": 3 },
      "npc_state_delta": { "chen_haisheng": { "happiness": 1 } }
    }
  ],

  // ── 失败兜底 ──
  "on_missed": {
    "action": "escalate",
    "description": "若 latest_by 到期仍未触发，陈海生怨气 +15，邪教传播 +10，顾沉舟改为通过何老三间接接触"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 唯一标识 |
| `name` | string | 中文名称 |
| `type` | enum | `anchor`=必须精确触发，不可跳过；`key`=必须在 `latest_by` 前触发，时机灵活；`opportunity`=可选触发，条件满足时才考虑 |
| `earliest` | {week, day} | 最早可触发时间，防止剧情过早发生 |
| `latest_by` | {week, day} | 最晚触发时间。编剧 Agent 需在此时间前完成编排 |
| `preferred_slot` | string | 建议时段，非强制 |
| `preferred_location_hint` | string | 建议地点，编剧 Agent 可根据 NPC 实际位置调整 |
| `participants` | string[] | 参与 NPC ID 列表 |
| `required_participants` | bool | 是否需要全部到齐 |
| `prerequisites` | string[] | 前置条件（自然语言，编剧 Agent 自行判断） |
| `block_if` | string[] | 阻断条件（满足任一则跳过此 beat） |
| `what_must_happen` | string | **核心字段**。用自然语言描述这个 beat 必须发生的叙事内容。编剧 Agent 据此生成具体事件 |
| `narrative_goal` | string | 这个 beat 的叙事目的。帮助编剧 Agent 理解"为什么要这个事件" |
| `outcomes` | OutcomeDef[] | 可能的结果分支，复用旧版 Outcome 的 delta 结构 |
| `on_missed` | object | 超时未触发的兜底处理 |

## 5. 编剧 Agent 与 NPC Agent 的协作协议

### 5.1 单时段工作流

```
时段推进
  │
  ├── ① 所有 NPC 并发调用 think() → 产出意图列表
  │     意图格式：{ npc_id, action_text, suggested_location }
  │
  ├── ② 编剧 Agent 读取：
  │     - StoryOutline（本文件定义的大纲）
  │     - 所有 NPC 意图
  │     - 当前游戏状态（时间、资源、缘线、业线）
  │     - 历史记录（已触发的 beat 列表）
  │
  ├── ③ 编剧 Agent 对每个 NPC 意图做三选一判决：
  │
  │     ┌─ 放行（无冲突）
  │     │   NPC 意图与大纲无冲突，不做任何干预。
  │     │   → 不注入记忆，不覆盖位置。
  │     │
  │     ├─ 软引导（轻度偏离）
  │     │   大纲有相关节点，但 NPC 还没往那边想。
  │     │   → 调用 agent.remember() 写入一条暗示记忆。
  │     │   → NPC 下次 think() 会检索到，自然调整行为。
  │     │   → 示例：大纲要求陈海生去港口，但他想去酒屋。
  │     │     注入："今天收工后，你隐约觉得港口那边有人在等你。"
  │     │
  │     └─ 硬编排（关键节点 + 即将到期）
  │        latest_by 即将到期，或锚点事件必须触发。
  │        → 调用 agent.dynamic.set_location() 直接移动 NPC。
  │        → 生成锚点事件，保证叙事节点不 miss。
  │        → 示例：Day 9 顾沉舟还在闲逛 → 强制拉到港口。
  │
  ├── ④ 编剧 Agent 生成事件列表（结构化输出）
  │     每个事件包含：EventTemplate + 选定的 Outcome
  │     可复用旧 CSV 中的事件作为素材
  │
  ├── ⑤ execute_events() 执行结算
  │
  └── ⑥ 标记已触发的 beat（写入历史记录）
```

### 5.2 软引导协议

编剧 Agent 调用现有 `agent.remember()` API，不引入新接口。

```python
# 软引导示例
agent.remember(
    day=current_day,
    slot=current_slot,
    description="收工后经过港口时，你注意到一艘陌生的夜船。船上的男人朝你点了点头，你觉得他有些眼熟。",
    importance=6,           # 略高于日常记忆（5），确保会被检索到
    emotion=Emotion.NEUTRAL
)
```

记忆注入后，NPC 的 `think()` 在下一个时段会通过 `RetrievalPipeline` 检索到这条记忆，自主决定是否响应。**NPC 仍可能选择忽略**——这正是软引导和硬编排的本质区别。

### 5.3 硬编排协议

仅在以下情况触发：
- beat 的 `type == "anchor"`（锚点事件，不可跳过）
- beat 的 `latest_by` 在 2 天内即将到期
- 前置 beat 已完成，当前 beat 的参与者长时间无交集

```python
# 硬编排示例
agent.dynamic.set_location(npc_id, Location.PORT)
# 然后编剧 Agent 生成一个锚点事件，将参与者绑定到该位置
```

硬编排后，NPC 仍参与事件中的对话和情绪反应（通过 `agent.respond()` 或事件执行后的记忆写入），但**不参与"去哪"的决策**。

## 6. 存档与序列化

### 6.1 运行时状态

编剧 Agent 需要追踪"哪些 beat 已经触发"，这部分数据存入 `GameSession`。

```python
@dataclass
class StoryState:
    """编剧 Agent 的运行时状态，需序列化为存档的一部分。"""
    triggered_beats: Dict[str, TriggeredBeat]  # beat_id → 触发记录
    active_interventions: List[Intervention]    # 当前活跃的记忆注入
    arc_progress: Dict[str, float]              # arc_id → 完成进度 (0.0–1.0)

@dataclass
class TriggeredBeat:
    beat_id: str
    triggered_day: int
    triggered_slot: str
    selected_outcome_id: str
    participants_present: List[str]
```

### 6.2 存储格式

大纲文件本身存储在 `design/data/story_outline.json`，是**静态策划数据**，不入存档。

存档只存 `StoryState`——即运行时推进状态。加载存档时，编剧 Agent 重新读取静态大纲 + 恢复运行时状态，继续编排。

## 7. 完整示例

### 7.1 一个 W2 时段的编排过程

**大纲要求**：W2 启动邪教渗透线。beat `gus_arrive`（锚点）已在 Day8 触发。beat `gus_contact_chenhai`（关键）的 `latest_by` 是 Day21，尚早。

**当前状态**（Day10 Night）：
- 顾沉舟：`think()` 返回 "在港口观察来往船只，熟悉地形"
- 陈海生：`think()` 返回 "去酒屋喝一杯，今天修网太累了"
- 其他 NPC 各自有意图

**编剧 Agent 判决**：

1. 顾沉舟的意图与大纲一致（在港口活动），**放行**。
2. 陈海生想去酒屋。大纲需要他接触到顾沉舟，但 beat 的 `latest_by` 还早（Day21），且 `preferred_location_hint` 是 "port"。编剧判断：**软引导**。

   ```python
   agent.remember(day=10, slot=Slot.NIGHT,
       description="酒屋的米酒涨价了。酒屋老板娘随口提起，港口何老三那边最近有便宜的私酿酒。",
       importance=6)
   ```

3. 不生成事件——等待陈海生自然走向港口。

**Day13 Night**：陈海生的 `think()` 检索到之前注入的记忆，产出了 "去港口看看能不能买到便宜酒"。编剧发现两人都在港口 → 时机成熟 → **生成事件**：顾沉舟在港口偶遇陈海生，以"老渔民"身份搭话，触发 `gus_contact_chenhai` beat 的 success 分支。

### 7.2 硬编排场景

**Day20**：`gus_contact_chenhai` 仍未触发。`latest_by` 是 Day21，仅剩 1 天。

**编剧 Agent 判决**：不能再等了。陈海生今晚必须去港口。

```python
# 硬编排
agent.dynamic.set_location("chen_haisheng", Location.PORT)
# 在陈海生记忆里补一条：你也不知道为什么，今晚就是想一个人去港口走走。
agent.remember(day=20, slot=Slot.NIGHT,
    description="今晚心里莫名烦躁，不想去酒屋，一个人走到港口吹风。",
    importance=5)
```

**生成锚点级事件**：陈海生在港口遇到顾沉舟。编剧 Agent 把这次触发标记为"强制"（因为 `latest_by` 已耗尽）。

## 9. 边界与限制

| 情况 | 处理 |
|---|---|
| 编剧 Agent 连续软引导无效 | 硬编排兜底（`latest_by` 到期前 2 天强制干预） |
| 某 beat 的参与者已死亡/离岛 | 触发 `block_if`，beat 标记为 `skipped`，`on_missed` 文案写入历史记录 |
| 编剧 Agent 生成的事件与 NPC 意图矛盾 | 硬编排优先。NPC 意图被覆盖，但 NPC 记忆里会写入一条"命运感"记忆 |
| LLM 不可用 | 降级到旧版 `match_events()` CSV 匹配逻辑 |
| 同一时段多个 beat 争用同一 NPC | 按弧线优先级排序：anchor > priority=0 > priority=1 > priority=2。低优先级 beat 延后 |
| 编剧 Agent 生成事件超时 | 硬限制：每时段最多生成 3 个事件。超出的延后到下一个时段 |
