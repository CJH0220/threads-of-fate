## 2. 游戏核心（一分钟版）

- **定位**：土地公视角的 60 天海岛小镇命运干预 / AI 原生叙事模拟。
- **玩家扮演**：归潮镇土地公「岛爷」。不能直接操控 NPC，只能用有限神力做**托梦 / 赐福 / 牵引机缘 / 遮蔽灾兆 / 显灵警示**五类间接干预。
- **一局时长**：60 天 × 3 时段（早 / 午 / 晚）= 180 决策窗口，7 天一周结算，第 60 天迎来天灾终局。
- **主要目标（三层）**：
  1. 表层：60 天后香火 ≥100 维持神位。
  2. 中层：让 14 位 NPC 沿自己的业线走向不同结局。
  3. 深层：领悟归潮镇的命运。
- **失败条件**：香火 < 100 被贬 / 触发四类强硬不幸结局（寺庙火灾、异教徒入侵、寺庙事故、超 50% 岛民叛教）。
- **5 种主结局**：失败 / 邪神 / 天界善神 / 中性 / 传奇（按香火 + 阴德 + 阳德阈值判定，AI 生成个性化后日谈）。
- **两条隐藏拉扯**：天界（绩效通牒）vs 地府邪神（阴德诱惑）。
- **核心随机器**：命运硬币 = 抛 N = 能力值 − 需求值 枚硬币，≥1 正面即成功；神力可微调概率或增减硬币数。

## 3. 后端现状（`src/backend/`）

技术栈：**FastAPI + Uvicorn + Pydantic v2 + httpx**（异步）。会话为**全局单例**，尚未支持多局并发。

### 3.1 模块地图

```
GameSession (engine/game_session.py) — 存档单元 / 全局单例
├── time     TimeState        60 天 × 3 时段 = 180 决策窗口
├── resource ResourceState    香火 / 神力 / 阴德 / 阳德
├── agents   AgentManager     14 个 NpcAgent
│              └─ NpcAgent = static + dynamic + memory + semantic + llm + bond_manager + pipeline
├── bonds    BondManager      NPC↔NPC 有向缘线
└── karma    KarmaManager     业线（多节点进度）
```

### 3.2 对外通道分工（重要）

- **REST**（`routes/game.py`）：新游戏 / 查状态 / 单条对话 / 存读档。**不推进时间、不触发事件**。
- **WebSocket** `/ws/game`（`routes/ws_game.py`）：**唯一能推进时段（`advance_time`）的通道**，事件结算、NPC 并发决策、旁白都在这里。前端主循环必须走 WS。
- **单连接限制**：`ws_game.py:30` `_active_ws` 只支持单局；`state.py:107` 会话为模块级单例。

### 3.3 HTTP 路由清单

| 方法 | 路径 | 用途 | 备注 |
|---|---|---|---|
| GET | `/health` | 健康检查 | `health.py` |
| POST | `/new-game` | 新建游戏 | `game.py:24` |
| GET | `/state` | 查询完整状态 | `game.py:46` |
| POST | `/chat/{npc_id}` | 与 NPC 对话 | `game.py:68`；speaker 固定「土地公」 |
| POST | `/save/{slot}` | 存档（0=自动，1-3=手动） | `game.py:93` |
| POST | `/load/{slot}` | 读档 | `game.py:108` |
| GET | `/saves` | 列出全部槽位 | `game.py:140` |
| DELETE | `/saves/{slot}` | 删除存档 | `game.py:154` |

### 3.4 WebSocket 消息类型

**入站**：`new_game` / `load_game` / `save_game` / `get_state` / `chat` / `advance_time` / `apply_intervention`
**出站**：`game_created` / `game_loaded` / `game_saved` / `game_state` / `game_over` / `time_advanced` / `event_triggered` / `npc_actions_start` / `npc_action` / `settlement_complete` / `narrator_beat` / `npc_response` / `intervention_applied` / `error`

**`advance_time` 主循环**（`ws_game.py:97`）：
```
can_advance? → time.advance → 发 time_advanced
  → (跨天) resource.apply_daily
  → 采集 NPC 位置 + C 级 NPC 固定位置 → match_events → execute_events
  → 逐事件发 event_triggered，并 bonds.apply_delta / karma.apply_delta
  → 发 npc_actions_start → S/A 级并发 think → 逐条 npc_action
  → 发 settlement_complete
  → (night) narrator → 发 narrator_beat
```

### 3.5 AI 层

- **LLM 客户端**：`_create_llm_client()`（`state.py:39`）按环境变量 `LLM_BACKEND` 切换。默认 `"llama"` → `LoadBalancedClient`（OpenAI 兼容协议，多端点 round-robin + Semaphore + failover）；`"anthropic"` → `AnthropicClient`（火山方舟 Ark 兼容端点）。**统一降级契约**：LLM 失败 / 无 token → `chat` 返回 None → 上层规则兜底。
- **Narrator**：`ai/narrator/narrator.py`，仅在 night 时段生成 ≤80 字土地公第一人称旁白，非阻塞。
- **NPCAgent 记忆系统**：三层组合（static / dynamic / memory）+ 双向量存储（TfidfVectorStore 默认 / EmbeddingVectorStore）+ 艾宾浩斯遗忘曲线检索 + 语义图谱 SemanticStore。参见 `src/backend/ai/npc_agent/NPCAgent记忆系统设计.md`。
- **NPC 分级**：S 级 6 人 + A 级 5 人 + B 级 3 人（并发 LLM think）；C 级 4 个群体/使者在 `ws_game.py:134` 硬编码位置，不参与 think。

### 3.6 引擎子模块

| 子模块 | 关键类 | 关键行为 |
|---|---|---|
| `engine/time/` | `TimeState`, `WeekPhase` | `advance/can_advance/peek`；60 天 night 后抛 `GameTimeExceededError` |
| `engine/resource/` | `ResourceState` | `apply_daily`（香火 -1、神力回满）；`apply_weekly` 定义了公式但**未接入主循环**（🔴 见 §7） |
| `engine/bond/` | `BondManager`, `Bond` | 5 类关系（红/金/蓝/灰/黑）× 0-100 强度 × 有向边；带别名表与 `_bond_key_map` |
| `engine/event/` | `EventTemplate`, `Outcome`, `SettlementResult` | 从 `design/data/事件配置表.csv` 加载；`weight ≥ 1000` 必触发 |
| `engine/karma/` | `KarmaManager`, `KarmaLine`, `KarmaNode` | 从 `业线节点表.csv` 加载；progress 0-100 阈值推进 |

### 3.7 数据与存档

- **运行时存档**（`storage/json_storage.py`）：目录 `saves/`（与 `src/` 同级）。槽位 0 → `autosave.json`，1-3 → `slot_N.json`；`index.json` 存元数据。存档内容 = `GameSession.to_dict()`（只存增量，静态数据从 CSV 复原）。
- **设计期图谱**（`graph_storage/`）：邻接表 + edge dict，**运行时未引用**，仅用于设计期离线可视化。
- **CSV 数据源**：`design/data/` 共 11 份（NPC 基础、业线节点、事件配置、事件结果、周阶段、地点配置、干预技能、本地化文本、结局判定、缘线初始关系、资源数值）。

### 3.8 测试覆盖（`src/backend/tests/`）

8 份测试：`test_time` / `test_resource` / `test_bond` / `test_karma` / `test_event` / `test_npc_agent`（最大，48+ 用例）/ `test_graph` / `test_storage`。架构文档自称 308 用例。**盲区**：所有单测覆盖组件级，未测 WS 端到端流程 → §7 的 4 个 bug 都被单测漏掉。

## 4. 前端现状（`godot/`）

**引擎**：Godot **4.4**，`gl_compatibility` 渲染器。视口 1280×720。默认纹理过滤 = 最近邻（像素风）。

### 4.1 主结构

- **主场景**：`res://scenes/main/Main.tscn` + `scripts/app/main.gd`。
- **Autoload 4 个**：`Settings` / `TutorialState` / `Backend` / `PortraitService`。
- **屏幕切换模式**：常驻覆盖层（结算/暂停/设置/结局等靠 `visible` 开关）+ 可替换 `ScreenRoot`（主菜单 / HUD 切换销毁重建）。
- **主玩法入口**：`MainGameUI.tscn` + `main_game_ui.gd`。

### 4.2 双模式适配器（这是前端最关键的架构）

前端不是"纯 mock"也不是"纯联网"，而是**同一套 UI + 两个可互换的状态适配器**（鸭子类型，方法签名完全一致）：

| 适配器 | 文件 | 特征 |
|---|---|---|
| MockGameState | `scripts/adapters/mock_game_state.gd`（528 行） | 从 5 份 JSON 读数据，本地实现时间推进/命运硬币/结局判定 |
| BackendGameState | `scripts/adapters/backend_game_state.gd`（719 行） | 走 Backend 收发；若后端不可达内部还有一层 `_mock_advance_time` 兜底 |

- **开关**：`main.gd:61` `const USE_BACKEND := true`。`Backend.check_health()` 10 秒超时或非 200 → 自动降级 Mock。
- **重要约定**：**静态富字段（人物描述/日程/羁绊/干预定义）始终从本地 JSON 读**；后端只推送动态的位置/情绪/资源。这意味着即使联网，`godot/data/mock/` 里的静态设定仍是权威。

### 4.3 六大核心面板

| 面板 | 显示 | 关键信号 |
|---|---|---|
| CharacterPanel | 头像、身份、日程、状态、四维、羁绊列表、业线进度 | `chat_requested(npc_id, name)` → 仅真实后端才开 NpcChatDialog |
| LocationPanel | 空镜背景、名称、描述、"此刻在此"头像行、三时段在场、该地点事件 | 纯展示，无按钮 |
| EventPanel | 事件名、风险、地点、类型、描述、参与者、可用干预按钮 | `enter_requested` → 进 DialogueEventScreen；`intervention_applied(event_id, intervention_id)` |
| SettlementPanel | 命运硬币结果、资源变化、人物变化、事件结果 | `closed()` |
| DestinyView（业线） | 每个 NPC 一张卡：业线名、进度、状态；筛选全部/有风险 | `character_selected` / `ending_requested`（进度≥100） |
| BondView（缘线） | 按人物分组的关系列表（符号+对象+关系+Lv+强度） | `character_selected` |

### 4.4 网络对接（全部集中在 `scripts/app/backend_client.gd`）

- 服务端地址：`http://127.0.0.1:8000`（用 IPv4 回环避开 Win localhost 的 IPv6 问题）。
- HTTP：`/health`（`:98`）、`/new-game`（`:150`）、`/state`（`:178`）。
- WebSocket：`/ws/game`（`:209`），断线 3s 自动重连。
- WS 发消息：`advance_time` / `chat` / `get_state` / `apply_intervention` / `save_game` / `load_game`。
- WS 收消息分发在 `_dispatch_ws_message`（`:263`）。

### 4.5 UI 主流程

```
启动 → check_health → (健康) BackendGameState + connect_ws
                    ↘  (失败) MockGameState
        → MainMenu → [新游戏] → HUD + 序章 VN → 主地图教程
        → 主循环（观察→干预→advance_time→SettlementPanel→…）
        → 每 7 天夜后 → WeekSummaryScreen
        → 第 60 天夜后 → run_finished → GameOverScreen 或 FinalSummary → EndingScreen
```

## 5. 前后端契约现状（`前后端交付案.md` v1.0）

契约文件已把 REST 端点、WS 消息、`GameStateResponse` / `NpcSnapshot` 定义清楚，Pydantic 模型作为前后端合同。**已在契约里明确写出的坑**：

- **时段枚举**：后端 `morning / noon / night`；前端 `Morning / Afternoon / Night`。在 `BackendGameState._normalize_state` 里做双向转换。
- **`static` 是 GDScript 保留字**：`NpcSnapshot.static` 在前端要重命名为 `npc_static`（`_normalize_npcs`）。
- **前端 Mock 有后端不认识的地点**：`wine_bar / seafood_shop` 在后端 Location 枚举里没有，酒屋/海鲜铺相关事件目前只能走 Mock。

### 5.1 契约与实现的差异（需要对齐）

| 项 | 主案 / 系统文档定义 | 契约与代码现状 | 处理建议 |
|---|---|---|---|
| 神力上限 | 周结算动态调整，Clamp(5, 20)（`§10.3`、`system/资源系统.md`） | `_normalize_state` 写死 max=10；`ResourceState.apply_weekly` 未被主循环调用 | 后端接入 apply_weekly、契约标注 max 动态 |
| 干预消耗 | 托梦 3 / 赐福 2 / 引导 5 / 遮蔽 8 / 剪断 10（`§10.2`） | `apply_intervention` 示例硬编码 `cost=2` | 契约与前端 UI 从 `干预技能表.csv` 读 |
| `/intervene` REST | ADR §1.6 列为 `POST /intervene` | 实际改走 WS `apply_intervention`，REST 无此端点 | ADR 与主案改为「干预走 WS」 |
| `divine_power` 语义 | 当前值 | REST 返回 max（`game.py:37/59/131`）；WS 返回当前值 + max（`ws_game.py:335`） | REST 修 bug，两端一致 |
